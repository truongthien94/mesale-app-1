# DEC-20260810-003 - One-time Post-registration Referral Decision

- Date: 2026-08-10
- Session: `SES-20260810-002`
- Status: accepted for Round 5

## Decision

Use a nullable `users.referral_prompt_decided_at` timestamp as the internal one-time decision marker. The authenticated endpoint accepts exactly one of `{ "referral_code": "..." }` or `{ "skip": true }`; a valid apply or explicit skip sets the timestamp, while invalid, same-IP, and self-referral attempts leave it null. Existing users are backfilled from `created_at` (or the database current timestamp).

Expose `referral_prompt_pending` in both the shared auth token user payload and `GET /account`, derived only from the timestamp and the referral feature flag. Mobile routes verification and 2FA continuations before the referral screen, and never displays the internal decided state.

## Rationale

The backend remains authoritative for exactly-once financial/referral state, concurrent decisions, anti-fraud checks, and feature flags. Returning the pending flag in the token payload avoids a post-auth routing flash, while `/account` remains the refresh source after apply/skip.

## Consequences

- Registration no longer accepts or applies an inline referral code.
- Invalid codes remain retryable; a member must explicitly skip or successfully apply.
- No member-facing reset or admin override is added in this round.
- Production API flags and settings remain unchanged; release verdicts remain `NOT READY`.
