# DEC-20260809-008 - Keep Laravel and Expo in One Monorepo

- Date: 2026-08-09
- Timezone: Asia/Bangkok
- Status: accepted
- Session: `SES-20260809-004`

## Context

The migration repository contains both the existing Laravel product and the new Expo/React Native client. A prior blocker asked whether the repository should remain a monorepo or be reduced to mobile-only scope. The product owner confirmed that the current cashback workspace is the independent repository for `mesale-app` and approved continuing the migration with the Laravel and Expo sources together.

Laravel must remain the backend and business-data source of truth. The mobile app depends on Laravel API contracts, migrations, middleware, tests, and the Blade/CSS visual reference, so keeping both applications together provides a reviewable contract boundary during migration.

## Decision

- Keep the Laravel application and `mobile/` Expo application in this repository as an intentional monorepo.
- Preserve the existing Laravel history and directory structure; do not delete, replace, or move the backend merely to make the repository mobile-only.
- Keep mobile business access behind the versioned Laravel HTTPS API. The repository layout does not authorize direct database access, shared credentials, or a separate mobile business database.
- Run bounded Laravel and mobile checks in the same branch/PR while reporting their evidence separately.
- Do not create an empty/orphan default branch or rewrite shared history to change the repository shape.

## Consequences

- `BLK-SCOPE-001` is resolved and the related GitHub Issue may remain closed with the owner decision recorded.
- Pull requests can review API and native-client contract changes together, but must clearly separate backend, mobile, migration, and release risk.
- CI, secret scanning, ignore rules, and ownership reviews must cover both Laravel and Expo paths.
- Store release readiness still applies only to generated mobile artifacts; inclusion of Laravel source in the repository is not release evidence.
- A future repository split requires a new explicit decision, migration plan, history-preservation strategy, and credential/security review.

## Alternatives Not Chosen

- Mobile-only repository now, because it would separate the client from the actively changing API contract and visual/source references during migration.
- Empty/orphan default branch, because it would make comparisons misleading and risk unnecessary history complexity.
- Duplicating the Laravel database or business logic in mobile, because mesale.vn remains the single server-authoritative source of truth.
