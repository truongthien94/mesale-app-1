# DEC-20260812-011 - Deploy referral eligibility as an additive production patch

- Date: 2026-08-12
- Session: `SES-20260812-015`
- Checkpoint: `CKP-20260812-021`
- Status: accepted and deployed

## Decision

- Inspect the production migration ledger before deployment and run only the two referral eligibility migrations by exact path.
- Add both nullable columns at the end of `users`, without `after(...)`, table-wide update, default, index, or old-user backfill.
- Patch the older production snapshot by reviewed hunks only; do not copy current repository controllers, routes, models, or all pending migrations wholesale.
- Keep existing users ineligible. Give new unlinked registrations a server-authoritative 72-hour deadline; mark already-linked registrations decided immediately.
- Preserve the legacy inline referral registration behavior on the production snapshot for backward compatibility.
- Roll back application code if required, but retain nullable columns once new referral state can exist.

## Rationale

- Unscoped migration would have attempted seven unrelated schema/data changes with separate risk and dependencies.
- Additive nullable columns avoid rewriting old member records and make interrupted deployment recovery safer.
- A production-snapshot patch minimizes behavioral drift while closing the exact mobile/backend contract gap.
- Retaining columns during code rollback avoids destroying referral decisions created after deployment.

## Rejected Alternatives

- Running unscoped `php artisan migrate`.
- Backfilling every existing user as decided.
- Copying the repository's current controllers/routes/models wholesale to the older production snapshot.
- Dropping the new columns as the first rollback action.
