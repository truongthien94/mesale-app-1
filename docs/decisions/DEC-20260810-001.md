# DEC-20260810-001 - Idempotency Retention Policy

- Date: 2026-08-10
- Session: `SES-20260810-001`
- Status: accepted locally; deployment evidence pending

## Decision

Retain completed financial idempotency records for 24 hours, retain stale `processing` markers for seven days, and prune both in batches of 500 rows. Run the command daily at 03:20 with overlap protection. All values except the schedule time are configurable through Laravel configuration/environment values, and operators can use dry-run or explicit hour overrides.

## Rationale

Mobile retry keys are scoped to an active financial submission and remain stable across explicit retries. A full day preserves replay safety for normal network/offline recovery while bounding encrypted response retention. The service creates and completes its marker inside the same database transaction, so a multi-day `processing` row is abandoned rather than a legitimate request duration; seven days is a conservative safety window before releasing it.

## Consequences

- Reusing the same key after the completed retention window can execute a new mutation, so clients must not retry an abandoned submission after 24 hours without reconciling server state.
- Production rollout must verify the scheduler, row counts, runtime, locking, and monitoring before `BLK-DATA-001` is closed operationally.
- The existing middleware, API routes, and financial mutation semantics are unchanged.
