# DEC-20260809-009 - Deletion And Payout Integrity Policies

- Date: 2026-08-09
- Session: `SES-20260809-005`
- Status: accepted for local implementation; production deployment pending

## Context

Round 2 identified three store-blocking integrity gaps: Apple grants could survive password-confirmed account deletion, saved payout destinations were unique only within one member, and referral rows could cascade-delete when a referrer account was removed.

## Decision

- Choose Apple deletion option B. Do not persist a long-lived Apple refresh token. Every account with `apple_id` must complete fresh Sign in with Apple reauthentication; Laravel exchanges the authorization code, revokes the returned provider refresh token, and only then starts local deletion.
- Hard-block a normalized payout destination globally. The identity is SHA-256 over normalized payment method, provider name, and account number, protected by a database unique constraint. Cross-user claims return `ACCOUNT_ALREADY_CLAIMED`.
- Preserve `referrals` and `referral_commissions` when the deleted user is the referrer. Set `referrer_id` to null and retain amounts, level, status, referred member, and source order linkage. These tables contain no denormalized referrer PII.

## Rationale

- Option B avoids adding a new long-lived provider secret and closes the silent Apple-disconnect gap with a clear client action.
- A database constraint is the only reliable boundary for concurrent payout-account claims; application prechecks remain for clearer errors.
- Nulling the referrer key is a bounded, reversible schema design that preserves counterparty evidence without retaining the deleted user's profile.

## Consequences

- Apple-linked users must perform Apple Sign-In during deletion even when they also have a local password or Google identity.
- Legitimate shared family payout accounts are not supported unless product/fraud policy later introduces a reviewed exception workflow.
- Referral ledger retention is only the first bounded step. Retention periods and treatment of the wider financial ledger remain an owner/legal decision.
- Production rollout requires a read-only duplicate payout audit before the unique migration and staging/MariaDB verification.

## Rollback

- The payout constraint migration drops the unique index and `destination_hash` column.
- Referral FK rollback is allowed only before anonymized null-referrer rows exist; afterward rollback intentionally fails rather than delete or fabricate ledger identity.
- Apple option B can be replaced later by encrypted server-side refresh-token storage only through a separate reviewed migration and key-management design.
