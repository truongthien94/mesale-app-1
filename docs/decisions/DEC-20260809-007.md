# DEC-20260809-007 - Bound the First Financial Idempotency Rollout

- Date: 2026-08-09
- Timezone: Asia/Bangkok
- Status: accepted and applied locally
- Session: `SES-20260809-003`

## Context

Withdrawal creation and gift redemption can change a member balance and are vulnerable to duplicate client retries after a timeout. The wider API also contains retryable reward and account mutations, but extending a new persistence contract to every mutation without staging evidence would enlarge the risk surface. The current withdrawal account-number uniqueness check is application-level and has not been proven under real MariaDB concurrency.

## Decision

- Require `Idempotency-Key` for withdrawal creation and gift redemption in the first P0 correction.
- Scope stored keys by user and operation, store only the key hash and canonical request hash, and encrypt completed replay responses at rest.
- Replay the same completed request, reject the same key with a different request payload, and report an in-progress duplicate without repeating business side effects.
- Do not claim global idempotency coverage or M0 completion. Track retention/pruning as `BLK-DATA-001` and normalized cross-user payment-account uniqueness as `BLK-FIN-001`.
- Keep production Open API disabled until staging, operational retention, MariaDB concurrency and rollback evidence exist.

## Consequences

- The two highest-priority balance-changing routes now have isolated replay/conflict tests and a mobile-call contract.
- Stored encrypted replay rows can grow until a retention policy and scheduled pruning process are approved.
- Gift-code redemption, task claims, check-in, payment-account writes and other retryable mutations still require their own scoped rollout.
- A schema-backed normalized uniqueness strategy may require a migration and operational data review before production use.

## Alternatives Not Chosen

- Client-only duplicate-tap prevention, because it cannot protect against network retries or parallel clients.
- A single global key namespace, because unrelated operations could collide and authorization boundaries would be less explicit.
- Immediate production activation or blanket idempotency rollout without staging and database evidence.
