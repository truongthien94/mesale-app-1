# Codex Prompt — Round 5: Post-registration referral-code step

Source commit verified before this prompt: `83d20fa` on `main` (Round 4 already merged, working tree clean, CI green on `31328158427` and `31328340060`). Create new commits; do not amend history.

## Context (product decision, already made by the project owner — do not re-litigate)

Today the mobile registration form (`mobile/app/(auth)/register.tsx`) has an inline, optional "Mã giới thiệu" text field submitted together with the rest of the registration payload. The backend (`app/Http/Controllers/Api/V1/AuthController.php`, register method) reads `referral_code` from that same request, resolves it to a referrer via `User::where('referral_code', ...)->first()`, applies an anti-fraud same-IP block, and sets `referred_by` at `User::create()` time. There is no existing endpoint to apply a referral code to an account that already exists, and no existing "prompt dismissed" flag anywhere in the schema.

The owner wants this reworked into a distinct post-registration step:

1. Remove the referral-code field from the registration form itself.
2. After a new account finishes the *entire* signup flow (including mandatory email verification and/or 2FA, if those are enabled) and lands with a full authenticated session, show a new dedicated screen: "Enter your referral code" with a text input and a "Skip" button, before the user reaches `/home`.
3. If the user enters a valid code, apply it (same anti-fraud same-IP rule as today) and never show the screen again for that account.
4. If the user taps "Skip", never show the screen again for that account either.
5. If the user enters an invalid/rejected code (does not exist, or blocked by the same-IP anti-fraud rule), show an inline error and let them either correct the code or tap "Skip" — do NOT silently treat a bad code as an implicit skip, and do NOT mark the account as dismissed until the user explicitly skips or a code is successfully applied.
6. The "already decided" state (applied a code, or skipped) is an internal-only flag. It must never be surfaced to the user in any UI (no "you already skipped this" message, no settings toggle, nothing) — mobile simply asks the backend "should I show this screen" and gets a yes/no, with no user-facing explanation either way.
7. There is no user self-service way to reopen or redo this step once decided. (Whether an admin-only override exists later is out of scope for this round — do not build one now.)

## Task 1 — Backend: referral-code decision state + apply endpoint

1. Add a migration adding a nullable `referral_prompt_decided_at` timestamp column to `users` (name it exactly this; it is an internal bookkeeping field, not user-facing — no need for a separate "how" column since this round doesn't require distinguishing skipped vs. applied for any UI or business logic). Read `app/Models/User.php` first — note that sensitive columns are deliberately excluded from mass assignment via the `#[Fillable([...])]` attribute (see the comment block above it); add `referral_prompt_decided_at` to that list only if code actually needs to mass-assign it, otherwise set it explicitly like `email_verified_at` is set elsewhere in `AuthController`.
2. Remove `referral_code` handling from the `register` method in `AuthController.php` (the validation rule at line ~206, the referrer-lookup/anti-fraud block at lines ~219-230, and the `referred_by` value used at user creation). New accounts should always be created with `referred_by = null` and `referral_prompt_decided_at = null`.
3. Add a new authenticated endpoint, e.g. `POST /api/v1/account/referral-code`, that:
   - Requires an authenticated session (same auth middleware as other account-scoped routes — check `routes/api.php` for the existing pattern used by e.g. the `account`/`security` routes and match it).
   - Accepts `{ "referral_code": "<code>" }` (required, string, max 50) for "apply", or `{ "skip": true }` for skip. Decide the exact request shape yourself based on what's simplest to consume from the mobile client — document whatever you pick.
   - If the account already has `referral_prompt_decided_at` set, return an error (this step cannot be redone) — pick a clear error code, e.g. `REFERRAL_PROMPT_ALREADY_DECIDED`.
   - On "apply": look up the referrer by `referral_code`, apply the exact same same-IP anti-fraud rule that existed in the old registration code path (reuse `Setting::getVal('referral_enabled', ...)` and `Setting::getVal('block_same_ip_referral', ...)` the same way), set `referred_by`, create the `Referral` row and the referrer `Notification`, mirroring what the old inline registration code did — then set `referral_prompt_decided_at = now()`. If the code doesn't resolve to a real referrer or is blocked by the anti-fraud rule, return a validation-style error and do NOT set `referral_prompt_decided_at` (so the user can retry or skip).
   - On "skip": just set `referral_prompt_decided_at = now()`. No other side effects.
   - Note a user's own IP for the anti-fraud check should be read the same way the old code read it (`$request->ip()`) — by the time this endpoint is called the user is already authenticated, so use whatever the current request's IP is, not a stored value from registration time.
4. Add a boolean (e.g. `referral_prompt_pending`) to whatever endpoint mobile already polls right after auth completes to know what screen to show next — check `GET /account` (used by `getCurrentUser()` in `mobile/src/api/auth.ts`) and the `User` resource/serializer it uses, and add the field there rather than inventing a new endpoint. The value should be `true` only when `referral_prompt_decided_at` is null AND `Setting::getVal('referral_enabled', '1') === '1'` (if referrals are disabled entirely, never show the prompt).
5. Do not change any other existing account/session/auth endpoint contract or behavior. Do not touch the `idempotency.key` middleware or its 4 protected routes (unrelated to this round).

## Task 2 — Mobile: new post-registration screen + gating

1. Remove the "Mã giới thiệu (tùy chọn)" field from `mobile/app/(auth)/register.tsx` (state, JSX, and the `referralCode` passed to `register()`). Remove `referralCode` from `RegisterPayload` in `mobile/src/api/auth.ts` and its mapping in the request body.
2. Add a new screen (e.g. `mobile/app/(auth)/referral-code.tsx`, following the existing file/route conventions in that directory) with a text input for the code and a "Skip" (bỏ qua) button, matching the existing auth-screen visual style (see `verify-email.tsx` for the pattern of loading/disabled/error/notice states to reuse).
3. Wire the gating so this screen appears only once a user has a full authenticated `session` (i.e., after email verification and/or 2FA are already satisfied) AND the account's `referral_prompt_pending` (from `/account`) is true. Check how `session`/`user` state currently flows through `AuthProvider.tsx` (`acceptAuthenticated`, `user` state, `getCurrentUser()`) and the redirect guards in `register.tsx` (lines 25-27), `login.tsx` (lines 76-78), `verify-email.tsx` (lines 56-57), `two-factor.tsx` (lines 64-65), and `mobile/app/(tabs)/_layout.tsx` (line 12) — add whatever redirect/guard logic is needed so:
   - A user who still has `pendingAuth` (email verification or 2FA not yet done) is NOT shown this screen — they stay in their existing verification flow first.
   - A user who has a full `session` but `referral_prompt_pending === true` is redirected to `/referral-code` instead of `/home` (update `mobile/app/index.tsx` and `(tabs)/_layout.tsx`'s redirect logic, and the post-auth redirects in `register.tsx`/`verify-email.tsx`/`two-factor.tsx`/`login.tsx` accordingly).
   - A user with `referral_prompt_pending === false` (or the field absent/false, e.g. existing accounts created before this change) goes straight to `/home` as today — existing users must NEVER see this new screen retroactively, so make sure the migration backfill sets `referral_prompt_decided_at` to a non-null value (e.g. `now()` or `created_at`) for all pre-existing rows, not just new ones. This is important: an existing user base must not suddenly see a "step 1" prompt after this deploys.
4. Add an `applyReferralCode`/`skipReferralPrompt` API call (in `mobile/src/api/auth.ts` or wherever fits the existing module boundaries) hitting the new backend endpoint, and call `refreshUser()` (already exposed by `useAuth()`) after either action succeeds so `referral_prompt_pending` flips to false and the redirect guards naturally stop routing to `/referral-code`.
5. On invalid/rejected code: show the returned error message inline (reuse `FormErrorSummary`/`ApiError` patterns from `register.tsx`), keep the user on the screen, let them edit and resubmit or tap Skip. Do not auto-skip on error.
6. Do not add any user-facing text anywhere (this screen, settings, account screen, notifications) referencing "you already decided this" / "already skipped" — the flag is invisible to the user by design.
