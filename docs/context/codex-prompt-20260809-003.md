## Task 1 — Wire native Google/Apple sign-in on the mobile client

The backend `POST /api/v1/openapi/auth/oauth/google` and `.../oauth/apple` endpoints exist and are feature-flagged OFF by default. The mobile app currently has no way to call them.

1. Add the minimal Expo-compatible packages needed for native Google and Apple sign-in (e.g. `expo-auth-session` plus provider-specific pieces, or the current recommended Expo SDK 53-compatible approach — check what's actually compatible with Expo SDK 53 / RN 0.79.6 before picking versions, don't guess). Pin exact versions, run `npx expo install` where applicable so versions match the installed Expo SDK.
2. Add a mobile-side auth service function that: on Android/iOS obtains a Google ID token, POSTs it to `oauth/google` with `{id_token, device_name}`; and for Apple (iOS only — do not offer it on Android) obtains identity token + authorization code + nonce via Apple's native sign-in flow and POSTs to `oauth/apple` with `{identity_token, authorization_code, nonce, device_name}` exactly matching the backend's validation rules in `NativeOAuthController`.
3. Wire these into the existing login screen(s) under `mobile/app/(auth)/` as additional sign-in buttons, following the existing screen's UI patterns (read the existing login screen first, match its style/error-handling instead of inventing a new pattern).
4. Handle the existing response contract already implemented server-side: `two_factor_required` challenge response, `ACCOUNT_LINK_REQUIRED`, `OAUTH_EMAIL_UNVERIFIED`, `OAUTH_EMAIL_REQUIRED`, `OAUTH_IDENTITY_AMBIGUOUS`, `OAUTH_CREDENTIAL_INVALID`, `OAUTH_PROVIDER_UNAVAILABLE`, `OAUTH_REQUEST_IN_PROGRESS` — surface each as a distinct, user-readable message, don't collapse them into one generic "login failed" state.
5. Because both provider feature flags currently default OFF server-side (`api.enabled:auth_oauth_google`/`_apple`), the buttons must handle a `503`/`ENDPOINT_DISABLED`-style response gracefully (hide or disable the button, or show a clear "temporarily unavailable" state) rather than crashing — this flow needs to work today even with providers off, and later work when an owner turns the flags on.
6. Wire the same Apple identity/token capture into the account-deletion screen under `mobile/app/(tabs)/account/delete.tsx` so it can satisfy the backend's now-mandatory `APPLE_REAUTH_REQUIRED_FOR_DELETION` flow for any account with a linked Apple ID (Round 2 made this always-required — the deletion screen must be able to actually complete it, not just display the error).
7. Add mobile tests (contract/unit level, matching the existing test style in the repo) asserting the request payload shape sent to each endpoint matches exactly what the backend validators expect, and that each error code above maps to a distinct UI state.

Add public (no login required) pages reachable from a stable URL under the existing web app (`routes/web.php` + a matching Blade view or existing CMS/static-page mechanism — check if `Pages`/static page infrastructure already referenced in `docs/api/openapi-audit.md`'s `GET /pages/{slug}` can be reused before building a new route type):

Add these URLs to `mobile/app.json`/`app.config.ts` wherever Expo config or app metadata references a support/privacy URL, so the mobile app and store listings can point to the same URLs.
