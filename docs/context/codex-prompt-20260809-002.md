## Task 1 — Apple grant is not revoked when deletion is confirmed by local password

File: `app/Http/Controllers/Api/V1/AccountController.php`, method `validateDeletionConfirmation` (and `deleteAccount`).

Current behavior: `apple_refresh_token` is only placed on `$request->attributes` inside `validateAppleDeletionCredential()`, which only runs when the caller authenticates the deletion with `apple_identity_token`. If the account has both a local password AND a linked `apple_id`, and the user confirms deletion with their password (the normal/expected path for a password-having user), `deleteAccount()` never calls `revokeAppleRefreshToken()`. The account is deleted locally but the Apple Sign-In grant stays active on Apple's side — this violates Apple's account-deletion requirement (Guideline 5.1.1(v)) that deleting the account must also disconnect linked third-party auth grants.

Fix requirement: when `$user->apple_id` is not empty and the deletion is confirmed via password (not via a fresh Apple reauth), still revoke the Apple grant before the destructive delete transaction, using a stored Apple refresh token if one exists, or by requiring a fresh Apple reauth if no stored token is available. Do not silently skip revocation and do not block deletion silently either — pick one of:
- (a) If we do not currently persist a long-lived Apple refresh token anywhere at link time, add a column to persist an encrypted Apple refresh token captured at first sign-in/link time (mirroring how `apple_id` is stored), so a password-confirmed deletion can revoke it without demanding a second Apple login; or
- (b) If persisting a long-lived provider refresh token is judged too risky/complex for this round, require Apple reauthentication specifically for deletion whenever `apple_id` is set, even if a password is also present, and return a clear error code (e.g. `APPLE_REAUTH_REQUIRED_FOR_DELETION`) instructing the client to complete Apple Sign-In before password-confirmed deletion can proceed.

State in your commit message and completion report which of (a) or (b) you chose and why. Whichever you choose, do not weaken the existing Google/Apple identity-mismatch and ambiguity checks already in place. Add or extend PHPUnit tests covering: password-confirmed deletion of an Apple-linked account actually revokes the grant (or is correctly blocked pending reauth, depending on your choice), and that deletion still succeeds normally for accounts with no linked Apple identity.

## Task 2 — No cross-user uniqueness on payment accounts

File: `app/Http/Controllers/Api/V1/PaymentAccountController.php` (`store` method) and migration `database/migrations/2026_07_15_000000_create_user_payment_accounts_table.php`.

Current behavior: the only duplicate check is in-memory, scoped to the current user's own `UserPaymentAccount` rows (`payment_method` + `bank_name` + `account_number` match within `$existing`). Nothing prevents two different users from registering the same bank account number, and nothing prevents a race between two concurrent requests for the same user from creating duplicates before the `lockForUpdate()` on the `User` row takes effect versus a genuinely concurrent write.

This matters for the withdrawal flow's financial integrity (same destination account claimed by multiple member accounts is a fraud/dispute vector) and was flagged as an open item in a prior audit (`BLK-FIN-001`).

Fix requirement:
1. Add a migration that adds a proper composite index/constraint suited to detecting/preventing cross-user collisions on `(payment_method, bank_name, account_number)`. Decide and document whether cross-user duplicates should be hard-blocked at the DB level (global unique constraint) or only detected and flagged for manual review (index + application-level warning) — recommend the hard-block unless you find a legitimate reason two different members would need to share one payout destination (e.g. shared family account); if you find such a legitimate case in the existing product requirements or admin UI, downgrade to detect-and-flag and explain why in the migration's docblock and your completion report.
2. Update `PaymentAccountController::store` to enforce whichever policy you chose, with a clear API error code distinct from the existing per-user `DUPLICATE_ACCOUNT` (e.g. `ACCOUNT_ALREADY_CLAIMED` for hard-block, or include a `possible_duplicate` flag for detect-and-flag).
3. Add a regression test that creates the same `bank_name` + `account_number` for two different users and asserts the policy you implemented (rejection or flagged acceptance) — plus a concurrency-safe test (two near-simultaneous creation attempts) if practical with the current test setup.

## Task 3 — GitHub Issue #21 (`BLK-DATA-002`): financial ledger cascade-deletes on account deletion

Read `gh issue view 21` yourself before starting (do not rely on a paraphrase). Current `deleteAccount()` hard-deletes the `users` row and lets the DB cascade-delete `cashback_histories`, `withdrawals`, `referral_commissions`, `balance_logs`, and related financial history. This is a real compliance risk: tax/financial records for other parties (e.g. a referral commission paid to another still-active user, or a withdrawal that's part of the platform's own accounting ledger) can vanish, and it removes evidence needed for dispute resolution or regulatory retention.

This decision has legal/retention-policy weight beyond pure engineering, so implement the following as a bounded, reversible first step rather than a full redesign, and flag remaining open questions explicitly in your completion report and in the issue:

1. Before the destructive `$model->delete()` in `deleteAccount()` (self-service) and in Admin `UserController::destroy`/`bulkDestroy`, anonymize rather than physically delete rows that other parties have a legitimate interest in: for `referral_commissions` and any ledger/balance entries where this user is the *referrer* or *payer of record* to another still-existing user, do not cascade-delete them — instead null out/redact only this user's own PII fields reachable from those tables (if any exist there) while preserving the transactional amounts and the counterparty's referential integrity. For records that are purely this user's own history (`cashback_histories`, `withdrawals`, `balance_logs`, `daily_checkins`, `notifications`, `short_links` scoped only to this user with no counterparty), current cascade-delete behavior is acceptable to keep as-is for this round — do not over-scope this task into a full ledger redesign.
2. Add a short migration/model-level safeguard so `referral_commissions` rows are not cascade-deleted when the *referrer* user is deleted while the referred user still exists (check current FK `onDelete` behavior for `referral_commissions.referrer_id`/equivalent column first — read the actual migration, do not assume the column name).
3. Add a regression test: create user A referring user B, have a commission paid to A, delete A's account, assert B's referral history and the commission record still exist and are queryable, and assert A's own PII no longer appears in that record if it was ever denormalized there.
4. Update `docs/context/CURRENT.md`'s `BLK-DATA-002` line and comment on GitHub Issue #21 with what was actually implemented versus what remains open (e.g., long-term ledger retention policy is still an owner/legal decision, not something you should decide unilaterally).
