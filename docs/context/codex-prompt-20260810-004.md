## Task 1 — Idempotency key retention/pruning

1. Add a scheduled Artisan command (e.g. `idempotency:prune`) that deletes/archives rows from `idempotency_keys` older than a retention window. Read `app/Services/FinancialIdempotencyService.php` and `app/Models/IdempotencyKey.php` first to understand the existing `status` values (`processing`/completed states) and pick a retention policy that doesn't delete a `processing` row that might still be legitimately in-flight (e.g. only prune rows with a terminal status, or rows unconditionally older than a safe multi-day window regardless of status — check what "processing" can realistically mean in terms of max request duration before deciding).
2. Make the retention window configurable via `config/` (not hardcoded), with a sensible default (propose one based on how idempotency keys are actually used — check the financial write endpoints listed in Round 1's context: withdrawals, payment-accounts, tasks/claim, giftcode/redeem — and justify your choice in the completion report).
3. Register the command on Laravel's scheduler (`Schedule::command(...)->daily()` or equivalent for this Laravel version — check whether this app uses `app/Console/Kernel.php` or the newer `routes/console.php` `Schedule::` facade style, and match whatever pattern is idiomatic for the Laravel version already in `composer.json`).
4. Add a test that seeds old and recent `idempotency_keys` rows (varying status/age) and asserts the command prunes exactly the rows it should and leaves the rest untouched.
5. Do not change the existing `idempotency.key` middleware behavior or any of the 4 routes it's applied to (`routes/api.php:141,189,196,205`) — this task is retention only, not a behavior change to the idempotency check itself.

## Task 2 — Mobile dependency vulnerability remediation

1. Re-run `npm audit --json` in `mobile/` yourself first to get the current real advisory list (do not trust the counts in this prompt as fixed — they may have shifted since this was written) and categorize by whether the fix is `isSemVerMajor: true` or not.
2. For any advisory fixable WITHOUT a semver-major bump, apply the fix directly.
3. For the semver-major advisories (expected to be most of them — Expo SDK 57 and React Native 0.72 upgrades): do NOT blindly run `npm audit fix --force`. Instead:
   - Check what Expo SDK / React Native version is actually compatible with this project's current `expo`/`react-native` versions in `mobile/package.json`, and what the realistic upgrade path is (Expo SDK version bumps are typically done via `npx expo install expo@<version>` followed by `npx expo install --fix`, not raw `npm audit fix`).

Instead: (a) determine and document the exact target Expo SDK version that resolves the high-severity advisories, (b) identify what breaking changes that upgrade would introduce for this specific codebase (check Expo's official SDK upgrade changelog/migration notes for the relevant version jump), and (c) produce a written upgrade plan in your completion report rather than executing the upgrade in this round — this protects the working Round 1-3 OAuth/store-compliance work from an untested breaking change late in the release cycle.
   - Exception: if you find any advisory that is fixable with a safe, non-breaking patch/minor bump (not tied to the Expo SDK major version), apply it now and report it separately from the deferred-plan list.
4. After whatever direct fixes you apply, re-run `npm audit`, `npx expo doctor`, the mobile TypeScript typecheck, and the existing mobile test suite; report the before/after advisory counts and confirm nothing regressed.
